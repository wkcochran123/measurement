\chapter{The Forever Run and the Cost Dial}

The electron-pair interface is naturally cyclic, but the version used here now has one more electron in the
doorway. Start with the outer single-electron face. Let it touch the junction electron: an electron-electron
residual appears. Let that junction electron touch the pair ledger: the Cooper-pair face appears, the
pair-transfer count moves, and the phase ledger advances. Then unwind the pair face back to the junction electron
and the junction electron back to the outer electron. Nothing inside that four-stage alternation says it must
stop. The apparatus therefore needs two versions of the computation: the forever run, which expresses the cyclic
interface, and the cost-bounded run, which is the one an operator may safely execute.

\section{One Interaction Fold}

The fold is deliberately small:

\begin{quote}\small
\begin{verbatim}
def step (s : InteractionState) : InteractionState :=
  match s.stage with
  | .outerElectron =>
      { s with
        stage := .junctionElectron
        face := .junctionElectron
        electronElectronEvents :=
          s.electronElectronEvents + 1
        electronElectronResidual :=
          s.electronElectronResidual + 1
        costSpent := s.costSpent + 1 }
  | .junctionElectron =>
      { s with
        stage := .cooperPair
        face := .cooperPair
        pairTransfers := s.pairTransfers + 1
        pairEvents := s.pairEvents + 1
        phaseTurns := s.phaseTurns + 1
        costSpent := s.costSpent + 1 }
  | .cooperPair =>
      { s with
        stage := .returningElectron
        face := .junctionElectron
        pairTransfers := s.pairTransfers - 1
        singleEvents := s.singleEvents + 1
        phaseTurns := s.phaseTurns - 1
        costSpent := s.costSpent + 1 }
  | .returningElectron =>
      { s with
        stage := .outerElectron
        face := .singleElectron
        electronElectronEvents :=
          s.electronElectronEvents + 1
        electronElectronResidual :=
          s.electronElectronResidual - 1
        singleEvents := s.singleEvents + 1
        costSpent := s.costSpent + 1 }
\end{verbatim}
\end{quote}

The first arm makes the electron-electron contact and carries its residual forward. The second arm reads the
boundary as a pair event, increments the pair-transfer ledger, advances the phase-turn ledger, and spends one
cost unit. The third arm unwinds the signed pair and phase ledgers back to the junction electron. The fourth arm
unwinds the electron-electron residual and returns to the outer electron.

The model is not pretending that all superconducting contacts are this simple. It is isolating the recurrence
the user asked to put in. More detailed devices can replace \(\texttt{step}\) with a rule that consults
\(\Delta\), \(E_J\), \(E_C\), \(n_g\), temperature, parity lifetime, or an externally measured transition
probability. The first manual keeps the alternation visible.

\section{The Run That Should Not Be Evaluated}

Lean permits a partial definition whose computation need not terminate:

\begin{quote}\small
\begin{verbatim}
partial def runForever
    (s : InteractionState) : InteractionState :=
  runForever (step s)
\end{verbatim}
\end{quote}

This is the formal warning label. The function says what the unbounded interface does: it keeps applying
\(\texttt{step}\). If the user asks Lean to evaluate \(\texttt{runForever initial}\), the computation does not
come back with a final report. It has no reason to. The interface has been given an endless question, and it
answers by continuing to ask.

The forever run belongs in the file because it marks the physical shape of the problem. A superconducting
boundary can keep exchanging pair phase and parity events as long as it is driven. But the forever run is not the
operator entry point. It is the abyss with a label on it.

\section{The Cost-Bounded Run}

The total fold runner is still useful, because it gives the loop a decreasing natural-number argument:

\begin{quote}\small
\begin{verbatim}
def runWithCost : Nat -> InteractionState -> InteractionState
  | 0, s => s
  | budget + 1, s => runWithCost budget (step s)
\end{verbatim}
\end{quote}

Here the budget is the cost the operator is willing to spend, measured in interface folds. Lean accepts this
definition as a total function because the natural number decreases on every recursive call. The cost dial is not
a metaphor in the code; it is the argument that makes the computation terminate.

But the device-facing entry point is one layer sharper. The file also defines an elaborator command:

\begin{quote}\small
\begin{verbatim}
cooper_elab_run 12
\end{verbatim}
\end{quote}

That command runs the search during elaboration, spends the requested number of folds, stops there, and prints a
receipt. This is the correct shape for the forever interface. The unbounded search is present, but the elaborator
is the hand that cuts it off and reports what was seen before the cut.

The file proves the accounting clasp:

\begin{quote}\small
\begin{verbatim}
theorem runWithCost_spends :
    forall (budget : Nat) (s : InteractionState),
      (runWithCost budget s).costSpent =
        s.costSpent + budget := by
  intro budget
  induction budget with
  | zero =>
      intro s
      rfl
  | succ budget ih =>
      intro s
      simp [runWithCost, ih, step_spends_one,
        Nat.add_comm, Nat.add_left_comm]
\end{verbatim}
\end{quote}

This theorem is intentionally plain. It says the budgeted runner spends exactly the number of folds it was given.
If the runner is later changed to skip steps, double-spend steps, or hide a free interaction, this theorem is the
place where the accounting has to be repaired.

\section{How to Run It}

From the Lean project directory:

\begin{quote}\small
\begin{verbatim}
cd device
lake env lean Measurement/CooperManual.lean
\end{verbatim}
\end{quote}

This command runs the pairing-door experiment. It is the local check that the electron, the junction electron,
and the Cooper-pair face move through the intended four-stage cycle. The file evaluates six device cuts:

\begin{quote}\small
\begin{verbatim}
cooper_elab_run 0
cooper_elab_run 1
cooper_elab_run 2
cooper_elab_run 5
cooper_elab_run 12
cooper_elab_run 37
\end{verbatim}
\end{quote}

The budget \(0\) report stays at the outer electron with no cost spent. The budget \(1\) report stops at the
junction electron, carrying an electron-electron residual. The budget \(2\) report stops at the Cooper-pair face,
carrying both the electron-electron residual and the pair/phase residual. The budget \(3\) report returns to the
junction electron with the pair/phase residual unwound. The budget \(4\) report returns to the outer electron
with all residuals unwound. Larger budgets keep walking this same four-stage loop. The
\(\texttt{foundInteraction}\) field stays false. That is the point of the run. The device is not finding a hidden
stable electron--electron--Cooper-pair interaction. It is going around the loop, spending the elaborator budget,
and honestly saying that the three-way interaction witness has still not appeared.

The same file also prints the structural alpha ladder:

\begin{quote}\small
\begin{verbatim}
cooper_alpha_ladder 100
\end{verbatim}
\end{quote}

At a finite cut \(n\), the device reads the provisional loop-price approximation
\[
  \alpha_n \approx \frac{1}{n},
  \qquad
  \alpha_n^{-1} \approx n ,
\]
with the \(n=0\) row left empty because no loop price has yet been paid. This is not a fit to the physical
constant. It is the structural cost-ratio readout attached to the Cooper loop: one needle-through over the loop
cost paid so far. At \(100\), the printed row therefore reads \(\alpha_{100}\approx 0.01\) and
\(\alpha_{100}^{-1}\approx 100\), with no interaction witness found.

Do not confuse this structural ladder with the final alpha study in the next part. The Cooper manual answers the
question ``does the pairing-door loop advance, carry its residuals, and stop when budgeted?'' The final study
answers a different question: after the electron fact and carried decider are in place, what alpha aperture does
the machine read over repeated trials? The first run checks the interaction mechanism. The second run reads the
constant-facing receipt.
